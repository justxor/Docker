# 🧠 Модуль 1. Теория: как устроены контейнеры

[← На главную](../README.md) · [Следующий модуль →](02-install.md)

Команды забываются, а понимание остаётся. После этого модуля ты будешь знать, что контейнер — это не «лёгкая виртуалка», а обычный процесс Linux с хитрой изоляцией, — и половина «магии» Docker перестанет быть магией.

## 1.1. Какую проблему решают контейнеры

«У меня всё работает» — классика. Приложению нужны конкретная версия языка, библиотеки, системные пакеты, переменные окружения и настройки. На ноутбуке разработчика, на тестовом стенде и в продакшене всё это немного разное — и приложение ведёт себя по-разному.

**Контейнер упаковывает приложение вместе со всем окружением** в один переносимый артефакт — образ. Образ одинаково запускается везде, где есть совместимый рантайм.

| Было | Стало с контейнерами |
|---|---|
| Инструкция установки на 3 страницы | `docker run myapp:1.4` |
| Конфликты версий Python/Node/Java на одном сервере | Каждое приложение в своём контейнере со своими версиями |
| «Снежинки» — серверы, настроенные руками | Неизменяемые образы, собранные из кода (Dockerfile) |
| Откат = молитва | Откат = запуск предыдущего тега образа |
| Новый разработчик настраивает окружение день | `docker compose up` — и через минуту всё работает |

## 1.2. Виртуальная машина vs контейнер

```
   Виртуальные машины                    Контейнеры
┌───────┐┌───────┐┌───────┐       ┌───────┐┌───────┐┌───────┐
│ App A ││ App B ││ App C │       │ App A ││ App B ││ App C │
│ Libs  ││ Libs  ││ Libs  │       │ Libs  ││ Libs  ││ Libs  │
│Guest  ││Guest  ││Guest  │       └───────┘└───────┘└───────┘
│  OS   ││  OS   ││  OS   │       ┌─────────────────────────┐
└───────┘└───────┘└───────┘       │  Container runtime      │
┌─────────────────────────┐       ├─────────────────────────┤
│   Гипервизор            │       │  ОДНО ядро хоста (Linux)│
├─────────────────────────┤       ├─────────────────────────┤
│   Железо                │       │   Железо                │
└─────────────────────────┘       └─────────────────────────┘
```

| | Виртуальная машина | Контейнер |
|---|---|---|
| Что изолирует | Целый компьютер с собственным ядром | Процесс(ы) на общем ядре |
| Запуск | Десятки секунд — минуты | Миллисекунды — секунды |
| Размер | Гигабайты | Мегабайты — сотни мегабайт |
| Накладные расходы | Заметные (своё ядро, эмуляция железа) | Почти нулевые |
| Изоляция | Сильная (аппаратная виртуализация) | Слабее (общее ядро) |
| Другая ОС | Можно (Windows на Linux) | Только то же ядро: Linux-контейнеры на Linux |
| Типичное применение | Разные ОС, строгая изоляция арендаторов | Микросервисы, CI, dev-окружения, деплой |

💡 На macOS и Windows Docker Desktop запускает **маленькую Linux-VM**, а контейнеры живут внутри неё. Поэтому bind-mount там медленнее, а `localhost` контейнера — не совсем твой localhost.

💡 Эти подходы не конкуренты: в облаке контейнеры почти всегда работают **внутри** виртуальных машин.

## 1.3. Контейнер = процесс + namespaces + cgroups + своя ФС

В ядре Linux нет объекта «контейнер». Есть три механизма, из которых он собирается:

```
                 ┌──────────────── Контейнер ────────────────┐
                 │                                            │
  namespaces ──▶ │  ЧТО процесс видит: свои PID, сеть,        │
                 │  hostname, точки монтирования, юзеров       │
  cgroups    ──▶ │  СКОЛЬКО процесс может взять: CPU, RAM,     │
                 │  I/O, число процессов                      │
  rootfs     ──▶ │  КАКИЕ файлы процесс видит: ФС из образа   │
                 │  (OverlayFS)                               │
  + security ──▶ │  ЧТО процессу запрещено: capabilities,     │
                 │  seccomp, AppArmor/SELinux                 │
                 └────────────────────────────────────────────┘
```

### Namespaces — изоляция «что видно»

| Namespace | Что изолирует | Эффект в контейнере |
|---|---|---|
| **pid** | Дерево процессов | Приложение видит себя как PID 1, чужих процессов не видно |
| **net** | Сетевой стек | Свои интерфейсы, IP, порты, таблица маршрутов, iptables |
| **mnt** | Точки монтирования | Своя корневая ФС |
| **uts** | hostname и domainname | `hostname` контейнера = его ID или имя |
| **ipc** | Разделяемая память, очереди сообщений | Нет доступа к IPC хоста |
| **user** | UID/GID | root внутри может быть обычным пользователем снаружи (rootless, userns-remap) |
| **cgroup** | Видимость иерархии cgroups | Контейнер не видит чужие cgroups |
| **time** | Часы (ядро 5.6+) | Редко используется в Docker |

Убедись сам:

```bash
docker run -d --name demo nginx
docker exec demo ps aux 2>/dev/null || docker exec demo sh -c 'ls /proc | grep -E "^[0-9]+$"'
# внутри: nginx — PID 1

ps aux | grep "nginx: master"   # на хосте: тот же процесс с обычным большим PID
sudo ls -l /proc/$(docker inspect -f '{{.State.Pid}}' demo)/ns   # его namespaces
sudo nsenter -t $(docker inspect -f '{{.State.Pid}}' demo) -n ip a   # войти в сетевой namespace контейнера
```

### Cgroups — ограничение «сколько можно»

Без лимитов контейнер может съесть всю память и все CPU хоста. Cgroups (сейчас почти везде **cgroup v2**) ограничивают и считают ресурсы:

```bash
docker run -d --name limited --memory=256m --cpus=0.5 --pids-limit=100 nginx
cat /sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' limited).scope/memory.max
# 268435456
```

| Ресурс | Флаг docker run | Что будет при превышении |
|---|---|---|
| Память | `--memory=512m` | OOM killer убьёт процесс (код выхода 137) |
| CPU | `--cpus=1.5` | Троттлинг — процесс замедлится, но не умрёт |
| Процессы | `--pids-limit=200` | fork() вернёт ошибку (защита от fork-бомбы) |
| Диск I/O | `--device-write-bps /dev/sda:10mb` | Замедление |

### Rootfs и OverlayFS — «свой» диск

Образ состоит из **слоёв** — только для чтения. При запуске контейнера Docker кладёт сверху тонкий **записываемый слой** и склеивает всё через OverlayFS:

```
  Контейнер видит единую ФС (merged)
  ┌─────────────────────────────────────┐
  │  upperdir: записываемый слой        │ ← изменения контейнера (исчезнут с docker rm)
  ├─────────────────────────────────────┤
  │  слой 3: COPY . /app          (RO)  │
  │  слой 2: RUN pip install ...  (RO)  │  ← lowerdir: слои образа,
  │  слой 1: debian:bookworm-slim (RO)  │     общие для всех контейнеров
  └─────────────────────────────────────┘
```

- **Copy-on-write:** когда контейнер меняет файл из нижнего слоя, файл сначала копируется в верхний слой. Поэтому менять большие файлы в образе дорого.
- Удаление файла = запись «whiteout»-маркера в верхний слой; **в нижнем слое файл остаётся** — размер образа не уменьшится (важно для Dockerfile!).
- 10 контейнеров из одного образа занимают на диске место образа **один раз** + свои тонкие верхние слои.

```bash
docker inspect -f '{{json .GraphDriver.Data}}' demo | jq   # LowerDir, UpperDir, MergedDir
```

⚠️ Всё, что записано в записываемый слой, **пропадёт при удалении контейнера**. Данные храни в томах (модуль 6).

## 1.4. Образ, контейнер, реестр — главная тройка

```
  Dockerfile ──docker build──▶  Образ  ──docker run──▶  Контейнер
  (рецепт)                    (шаблон,                 (запущенный
                              неизменяемый)             экземпляр)
                                 │ ▲
                     docker push │ │ docker pull
                                 ▼ │
                              Реестр (Docker Hub, GHCR, Harbor…)
```

Аналогия из программирования: **образ — это класс, контейнер — объект** (экземпляр). Из одного образа можно запустить сколько угодно контейнеров.

### Имя образа по частям

```
  ghcr.io / justxor / myapp : 1.4.2 @sha256:9f86d08…
  ─────── ─────────  ─────   ─────  ───────────────
  реестр  namespace  репо    тег    digest (неизменяемый хэш)
```

- Реестр не указан → `docker.io` (Docker Hub).
- Namespace не указан → `library` (официальные образы): `nginx` = `docker.io/library/nginx`.
- Тег не указан → `latest`. ⚠️ `latest` — это просто тег по умолчанию, а **не** «самая свежая версия». Не используй его в продакшене.

## 1.5. Архитектура Docker

```
 ┌──────────────┐   REST API    ┌───────────────────────────────────────────┐
 │ docker CLI   │ ────────────▶ │ dockerd (Docker Engine)                   │
 │ (клиент)     │ /var/run/     │  образы, сети, тома, сборка (BuildKit)    │
 └──────────────┘ docker.sock   └──────────────────┬────────────────────────┘
                                                   │ gRPC
                                 ┌─────────────────▼────────────────────────┐
                                 │ containerd — жизненный цикл контейнеров,  │
                                 │ скачивание и хранение образов             │
                                 └─────────────────┬────────────────────────┘
                                                   │
                                 ┌─────────────────▼───────┐  ┌──────────────┐
                                 │ containerd-shim         │──│ runc         │
                                 │ (держит контейнер, даже │  │ создаёт ns,  │
                                 │  если dockerd упал)     │  │ cgroups, exec│
                                 └─────────────────────────┘  └──────────────┘
```

| Компонент | Роль |
|---|---|
| **docker CLI** | Клиент. Сам ничего не запускает — шлёт запросы демону |
| **dockerd** | Демон Docker Engine: API, образы, сети, тома, сборка |
| **containerd** | Промышленный рантайм (CNCF). Его же использует Kubernetes |
| **containerd-shim** | Прослойка на каждый контейнер: контейнеры переживают перезапуск dockerd (с `live-restore`) |
| **runc** | Эталонный OCI-рантайм: создаёт namespaces и cgroups и запускает процесс. Альтернативы: crun, gVisor (runsc), Kata Containers |
| **BuildKit** | Движок сборки образов |

🔴 Доступ к `/var/run/docker.sock` = **root на хосте**. Кто может писать в сокет — может запустить контейнер с `-v /:/host` и сделать что угодно. Поэтому членство в группе `docker` равносильно sudo.

## 1.6. Стандарты OCI и экосистема

**OCI (Open Container Initiative)** описывает три спецификации:

| Спецификация | Что описывает |
|---|---|
| **image-spec** | Формат образа: манифест, конфиг, слои (tar.gz) |
| **runtime-spec** | Как запустить распакованный образ (bundle) — это делает runc |
| **distribution-spec** | HTTP API реестра: pull/push |

Благодаря OCI образ, собранный Docker, запускается в Podman, containerd, Kubernetes, CRI-O — и наоборот.

| Инструмент | Что это |
|---|---|
| **Docker** | Самый популярный набор: CLI + демон + сборка + Compose |
| **Podman** | Совместимая замена Docker без демона, rootless по умолчанию (Red Hat) |
| **containerd / nerdctl** | Рантайм и Docker-совместимый CLI к нему |
| **CRI-O** | Лёгкий рантайм специально для Kubernetes |
| **Buildah, Kaniko** | Сборка образов без Docker-демона (удобно в CI и Kubernetes) |
| **Kubernetes** | Оркестратор: запускает контейнеры на кластере серверов |
| **Docker Desktop, OrbStack, Colima, Rancher Desktop** | Docker на macOS/Windows через Linux-VM |

## 1.7. Жизненный цикл контейнера

```
            docker create          docker start
  (образ) ─────────────▶ created ─────────────▶ running ◀────┐
                                                   │  │       │ docker unpause
                                     docker pause  │  └─────▶ paused
                                                   │
                       процесс завершился /        ▼
                       docker stop / kill      exited ──docker start──▶ running
                                                   │
                                          docker rm▼
                                               (удалён)
```

- Контейнер живёт, **пока жив его главный процесс (PID 1)**. Завершился процесс — остановился контейнер. Именно поэтому `docker run ubuntu` сразу завершается: bash без терминала сразу выходит.
- `docker stop` шлёт **SIGTERM**, ждёт 10 секунд, потом **SIGKILL**. Приложение должно корректно обрабатывать SIGTERM.
- Код выхода важен: `0` — успех, `137` = 128+9 — убит SIGKILL (часто OOM), `143` = 128+15 — SIGTERM, `126` — нет прав на запуск, `127` — команда не найдена.

### Проблема PID 1

В Linux процесс с PID 1 особенный: ядро **не применяет к нему обработчики сигналов по умолчанию**, и он должен «собирать» зомби-процессы. Если твоё приложение не умеет этого — оно не завершится по Ctrl+C / `docker stop` (будет ждать 10 секунд до SIGKILL) и может копить зомби.

Решения: запускать с `docker run --init` (добавит крошечный init — tini) или использовать exec-форму `CMD ["app"]` вместо shell-формы `CMD app` (подробности в модуле 5).

## 1.8. Принципы «правильного» контейнера

1. **Один контейнер — один процесс/одна ответственность.** Nginx, приложение и БД — три контейнера, а не один.
2. **Контейнеры одноразовые (ephemeral).** Их можно в любой момент удалить и пересоздать. Состояние — в томах или внешних сервисах.
3. **Неизменяемость.** Не правь контейнер руками через `exec` — поменяй Dockerfile и пересобери.
4. **Конфигурация через переменные окружения** (принципы 12-factor app), а не через разные образы для dev/prod.
5. **Логи — в stdout/stderr**, а не в файлы внутри контейнера.
6. **Минимальный образ.** Меньше пакетов — меньше уязвимостей и быстрее деплой.
7. **Не root.** Процесс внутри должен работать от непривилегированного пользователя.

## ✅ Проверь себя

1. Почему контейнер Linux нельзя запустить нативно на ядре Windows?
2. Какой механизм ядра не даёт контейнеру съесть всю память хоста?
3. Ты удалил в Dockerfile файл на 500 МБ отдельной инструкцией `RUN rm`. Почему образ не стал меньше?
4. Что произойдёт с данными в контейнере после `docker rm`?
5. Почему доступ к docker.sock опасен?

<details><summary>Ответы</summary>

1. Контейнер использует ядро хоста, а Linux-процессу нужны системные вызовы ядра Linux. Поэтому Docker Desktop поднимает Linux-VM (WSL 2).
2. cgroups (лимит `--memory`).
3. Файл остался в предыдущем слое; новый слой лишь помечает его удалённым. Удалять нужно в той же инструкции `RUN`, где он создан, или использовать multi-stage.
4. Записываемый слой удаляется вместе с контейнером — данные пропадут, если они не в томе.
5. Через сокет можно запустить привилегированный контейнер с корнем хоста внутри — это полный root-доступ.

</details>
